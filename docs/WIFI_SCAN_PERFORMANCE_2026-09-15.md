# Wi-Fi 扫描耗时优化

## 最终实现

- 按计划地址数配置设备发现并发：不超过 256 个地址为 32，不超过 1024 个为 48，更大网段为 64；实际工作数不超过地址数。
- 为阻塞式网络连接使用独立的有界 IO dispatcher 视图，并为组播与分析协调协程预留执行空间，避免工作协程增加后仍受默认 IO 并行度限制。
- 每个发现端口仍保留 450ms 连接超时，端口列表和设备分类规则保持原有逻辑。扫描没有固定总时长截止，全部地址和排队分析任务结束后才完成。
- 保留现有取消、网络错误、部分分析和覆盖范围提示。

## 验证中放弃的方案

尝试了快速探测再完整复查。96 并发、快速探测所有端口的一轮耗时 58,754ms，187 台设备、28 个摄像头线索，但 1654 个地址无法确认。64 并发、只快速探测一个端口的一轮耗时 68,142ms，196 台设备、28 个摄像头线索，但 1771 个地址无法确认。这两版没有作为交付方案，最终撤掉额外的快速探测，保留完整超时。

这些现象不能单凭一次扫描确定网络错误的根因；它们足以说明当前没有证据支持交付额外快速探测。

## 真机对比

使用同一台 PLY110 / Android 16、同一物理 Wi-Fi 的 /21 网段，VPN 保持开启。先前基线为 133,292ms、2046 个地址、189 台设备、28 个摄像头线索、2 个无法确认的地址。

| 指标 | 原有版本 | 最终版本 |
| --- | ---: | ---: |
| 总耗时 | 133,292ms | 67,606ms |
| 已检查地址 | 2046 | 2046 |
| 响应设备 | 189 | 189 |
| 摄像头线索 | 28 | 28 |
| 分析未完全结束的设备 | 5 | 5 |
| 因网络错误无法确认的地址 | 2 | 1 |
| 剩余排队分析任务 | 0 | 0 |

本次耗时减少约 **49.3%**。最终组播、mDNS、SSDP、ONVIF 通道均正常结束。发现探测的累计工作时间为 4,215,736ms（多线程累计值），接近原有 4,212,244ms；耗时下降来自并行处理，而非省略探测。最终指标在 `app/build/wifi-speed-bounded-metrics.log`，结果界面在 `app/build/speed-bounded-complete.xml`。

设备在线情况会随时间变化；单次结果数量不能证明召回率，也不能代表所有网络上的性能。
