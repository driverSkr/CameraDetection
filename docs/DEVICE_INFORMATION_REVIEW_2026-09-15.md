# 项目复查与设备信息完善

## 为什么设备信息不全

本轮确认并修复了采集、展示和保存之间的几处缺口：

- 详情页的型号原来固定显示“未知”，没有使用已有的 `brandModel` 字段。
- 服务探测只读取响应第一行，响应头中的 Server 信息没有采集；旧行读取器还可能一次读入并丢弃后续头部。
- mDNS 名称、主机名已有解析结果，但没有保存成独立设备字段，列表仍显示泛化类型。
- SSDP 只保存服务类型证据，没有保留 Server 描述。

## 本轮实现

| 信息 | 采集及展示方式 |
| --- | --- |
| 设备公告名称 | 来自 mDNS，列表和详情标题使用该名称，详情标明来源 |
| 主机名 | 来自 mDNS 的实际目标主机，保持原有端点归属逻辑 |
| 开放端口 | 仅记录实际连接成功的端口，发现阶段已连接成功的端口也保留 |
| 服务协议 | TCP、已确认 HTTP、已确认 RTSP；不按端口号直接判定服务 |
| 服务软件 | HTTP/RTSP Server 响应头，以及 SSDP Server 描述，显示端口或来源 |
| 公告服务类型 | 保留并展示 SSDP ST |
| 型号 | 展示已有型号字段，本机使用系统提供的制造商及型号；远端无可靠信息时明确说明 |
| MAC | 没有取得可靠值时解释缺失，不生成占位 MAC 或推断值 |

新增字段随历史保存；旧记录没有这些字段仍能正常读取。旧记录需要重新扫描才能补充信息。软件描述不等于硬件品牌或型号，新增元数据不参与摄像头分类规则。

响应读取共用原 1500ms 读取截止时间；头部最多 64 行、约 8KB，单行最多 4KB。只读取头部，不下载响应正文，不跟随设备给出的外部 URL。发现地址、TCP 超时和并发上限保持不变。

## 项目复核结论

本轮复核了新元数据与分类规则、进度/取消、历史缓存和兼容性、详情布局的交互，并回归相机、磁场、入口及订阅相关现有测试，未确认新的 P0/P1 阻断问题。不能据此认为所有硬件和网络情况均已覆盖。

仍有可继续完善的能力：

1. **远端品牌和型号**：目前没有实现 UPnP 设备描述文档、需认证的 ONVIF 设备信息或厂商协议查询。可考虑用户主动触发的“补充详情”，并约束为当前设备地址、有限响应大小和时间；不宜把所有额外查询塞入快速扫描。
2. **扫描中查看设备**：目前仍需扫描停止或完成后才能打开结果详情。这属于体验优化，可单独增加实时查看入口。
3. **现有覆盖限制**：IPv4 地址数上限和不支持 IPv6 的限制仍存在；HTTPS 端口目前只确认 TCP 开放，不代表已经识别 HTTPS 服务内容。
4. **专项验证范围**：未做真实支付、相机硬件故障注入和全机型兼容性验证，保留此前测试绕过配置。
