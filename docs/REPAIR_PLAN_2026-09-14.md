## P1-01：磁场真实读数与仪表比例分离

**修改范围**：[SensorPage.kt](/C:/Android/driverSkr/CameraDetection/app/src/main/java/com/spyfinder/hiddencamera/detectorapp/ui/main/page/SensorPage.kt)，提取可独立测试的磁场读数计算函数。

1. 用传感器 x/y/z 计算真实磁场幅值，作为唯一 μT 数据源；过滤 NaN、Infinity 和无效事件。
2. 保留独立的 0–100 仪表比例，只用于现有指针角度。修正显示值时不顺带改造量程或发明摄像头风险阈值。
3. 数字区域显示真实值，默认保留一位小数；平滑处理仅用于指针动画，避免把经过归一化的数值再写回读数。
4. 检测未开始、尚无有效事件或注册失败时显示“— μT”，不用 0 暗示已经测得零磁场；停止时恢复该待测状态。
5. 埋点将真实读数与仪表比例分开命名，避免继续把比例当物理量分析。

**验收**：输入 (30,40,0) 显示 50.0 μT；100 μT 不再显示 8 μT；强磁场使指针到量程上限但真实读数不被截断成 100；无效事件不使 UI 崩溃。原仪表外观保持。

## P1-02：统一连接结果分类

**修改范围**：[NetworkScanner.kt](/C:/Android/driverSkr/CameraDetection/app/src/main/java/com/spyfinder/hiddencamera/detectorapp/scan/NetworkScanner.kt)、[ScanRules.kt](/C:/Android/driverSkr/CameraDetection/app/src/main/java/com/spyfinder/hiddencamera/detectorapp/scan/ScanRules.kt)，新增共用探测结果类型与错误分类函数。

1. 分类为连接成功、明确拒绝、超时、网络不可达、取消、未知失败；发现与分析阶段使用同一分类器。
2. 优先读取异常原因链中的 errno。仅连接成功或明确 ECONNREFUSED 可作为本次 TCP 探测收到响应的依据；仍不凭此认定摄像头。
3. 不能识别的异常保守归入未知失败，不根据异常类名或本地化错误文案推断设备在线。
4. 分析时，明确拒绝表示该端口不可用；超时/网络不可达/未知失败标记分析未完成。其他探测已收集的有效证据继续保留。
5. 取消或资源关闭遵循扫描终止流程，不生成在线设备，也不误报为普通探测失败。

**验收**：故障注入覆盖 ECONNREFUSED、ENETUNREACH、EHOSTUNREACH、超时、无 errno 的 ConnectException 和取消；发现列表与分析完整性分别满足上述规则。此前已收到有效协议证据的设备不会因后续失败被删除。

## P1-03：完整读取有界的协议状态行

**修改范围**：NetworkScanner、[DiscoveryProtocols.kt](/C:/Android/driverSkr/CameraDetection/app/src/main/java/com/spyfinder/hiddencamera/detectorapp/scan/DiscoveryProtocols.kt)，新增可用流或本地 Socket 测试的状态行读取函数。

1. 循环读取至状态行结束，不等待整个响应体；容忍状态行跨任意多个读取片段。
2. 初始状态行上限 4 KiB，读取截止时间取“单次读取预算、单设备剩余预算、整轮剩余预算”的最小值。每次读取只消耗剩余时间，慢速分段不能不断延长期限。
3. 区分完整状态行、提前 EOF、超限、超时、取消。截断或未读完不算已完成的阴性判断。
4. 保持现有证据语义：合法 RTSP 401 等响应可产生视频协议线索，HTTP 响应或单纯开放端口不能代替视频协议证据。

**验收**：一次返回、按字节分段返回的合法状态行判断一致；RTSP 200/401 均通过；HTTP 正文包含 RTSP 字样不误判；超长行、慢速响应、断流及取消均在预算内退出并关闭 Socket。

## P2-01 + P2-02：统一探测端口，并将发现与分析并行推进

**修改范围**：NetworkScanner、ScanRules、[ScanViewModel.kt](/C:/Android/driverSkr/CameraDetection/app/src/main/java/com/spyfinder/hiddencamera/detectorapp/scan/ScanViewModel.kt)。这两项一起实施，避免增加端口后放大超时问题。

1. 共用一份探测定义：554/8554 使用 RTSP，80/5000 使用 HTTP，443 暂只记录 TCP 可达性。发现优先级先视频端口，再其他端口；发现到目标后交给服务分析。
2. UDP 发现与 TCP 探测均把新设备送入去重队列，不再等整个网段探测完才启动分析。视频协议广告线索优先，普通设备也能获得分析机会。
3. 先沿用可控的上限：最多 32 个发现任务、8 个分析任务，所有 Socket 纳入统一资源管理；限制队列与发现记录数量，超过限额明确标记覆盖受限。
4. 保留整轮 45 秒硬上限。初始调度方案为最迟约第 33 秒停止补充新的发现任务，将剩余时间用于排队设备分析；单设备最多 8 秒，所有超时都受整轮截止时间约束。该分配是可集中调整的参数，需模拟网络验证后确定。
5. 同一 IP 只保留一条设备记录；并发获得的证据合并，避免旧分析快照覆盖新组播证据。重复探测、并发进度乱序也需被去重或拒绝。
6. 进度使用实际已检查地址、已发现设备、已完成分析数；未知总设备量时不制造精确完成比例。沿用原雷达和百分比区域，只有完整完成才到 100%；未完成显示明确原因和实际覆盖数量。
7. UI 快照先按约 200ms 合并推送，终态立即刷新；按稳定设备键更新，减少逐设备全量排序、清空再填充。

**验收**：仅 8554 可达且其余端口静默丢包的设备能被发现；/21 模拟网段早期发现的视频目标能在扫描结束前得到分析机会；大量无响应地址不突破整轮预算；超预算结果明确为部分完成；发现、分析和 UI 均不会在取消后继续更新。以记录的并发数、Socket 关闭情况和时间分布验证，不预设性能提升百分比。

## P2-03：保存最近一次结果，同时保留最后完整结果

**修改范围**：[ScanHistoryStore.kt](/C:/Android/driverSkr/CameraDetection/app/src/main/java/com/spyfinder/hiddencamera/detectorapp/utils/ScanHistoryStore.kt)、[MainContextEntity.kt](/C:/Android/driverSkr/CameraDetection/app/src/main/java/com/spyfinder/hiddencamera/detectorapp/ui/main/context/MainContextEntity.kt)、ScanViewModel、原结果页顶部状态区。

1. 引入带版本的扫描记录：recordId、开始/结束时间、网络地址与前缀、扫描状态、计划/实际检查地址数、设备分析数、结束原因、设备证据及用户信任标记。
2. 分别保留“最近一次有结果的扫描”和“最后一次完整扫描”。部分、取消或失败结果只有在确实检查过目标或取得远端证据时才更新最近记录，避免刚点开始就取消覆盖有用记录。
3. 完整结果更新两个记录引用；部分结果只能更新最近记录。无论何种失败，最后完整记录都保留。
4. 单独、串行地执行持久化；主线程只捕获不可变快照，JSON 编码和写入移至后台。结束、取消和信任标记修改时及时保存；扫描中约每 3 秒写入检查点，避免每个设备触发磁盘写入。
5. 重启时将未结束的检查点恢复为“已中断”，明确完成度，不自动继续旧网络探测。突然杀进程最多可能丢失最近一次尚未持久化的检查点间隔，不能承诺零丢失。
6. 按版本兼容读取现有历史。无法确定完整状态的旧记录保留旧记录标识；新格式写入并成功读取校验后才启用，旧键暂不删除。
7. 信任标记按 recordId 与记录内设备键修改，不仅凭 IP 更新另一条历史，避免相同私网地址在不同扫描记录间串改。

**局部 UI**：历史仍使用原设备列表和详情弹窗；当最近记录与最后完整记录不同，在原结果页顶部增加同风格的“最近一次 / 上次完整”轻量切换，原状态文案显示完成状态和时间；只有一条记录时不显示切换。

**验收**：完整 A → 部分 B → 重启后，A/B 均可访问，B 有明确不完整提示；取消、进程中断和保存失败不破坏 A；旧版本历史仍能读取；修改 B 中的信任标记不影响 A。

## P2-04：历史入口不再依赖是否开始过扫描

**修改范围**：[DetectCheckView.kt](/C:/Android/driverSkr/CameraDetection/app/src/main/java/com/spyfinder/hiddencamera/detectorapp/ui/main/view/DetectCheckView.kt)、MainContextEntity。

1. 将“正在扫描”“有本次结果”“有历史记录”分别作为按钮显示依据，避免一个 isStartDetect 同时决定全部流程。
2. 扫描结束、失败或取消后，有历史就能打开历史；不通过简单清空本次状态来恢复入口。
3. 初始状态保留原“历史 + 开始”；已有本次结果时保留原“重查 + 结果”，在标题栏右侧补充小型“历史”文字入口，与现有皇冠并存。扫描进行中暂不可进入历史，以免误把实时结果当历史。
4. 查看历史、切换记录、返回本次结果均不触发重新扫描；重查仍由用户主动点击。

**验收**：已有历史 → 扫描 → 完成/取消/失败三条路径都能打开历史并返回本次状态；切换 Tab 不丢入口；中文版、英文版、小屏和大字体下标题栏无重叠。

## P2-05：相机控制只接收当前有效请求的结果

**修改范围**：[CameraScannerPage.kt](/C:/Android/driverSkr/CameraDetection/app/src/main/java/com/spyfinder/hiddencamera/detectorapp/ui/camera/page/CameraScannerPage.kt)。

1. 缩放请求带相机实例标识和递增序号；旧相机、旧请求、离开页面后的回调不能更新当前 UI。
2. 正确解包异步异常，忽略因新请求替代而产生的正常取消。生命周期导致的关闭按预览生命周期处理，不伪装成缩放故障。
3. 预览/权限错误与缩放/闪光灯控制错误分开；预览错误继续使用现有恢复面板，控制错误使用已有提示风格，避免遮挡正常预览。
4. 当前请求成功时只清除对应控制错误，不清除其他真实故障；切换相机时同步重置范围及请求代次。
5. 相同的有效性校验用于闪光灯回调，防止旧镜头回调改变新镜头的开关状态。

**验收**：快速往返拖动、拖动中切换镜头、拖动后退后台均不显示过期错误；真实失败可提示、成功后可恢复；原滑块、滤镜和镜头按钮保持。

## P2-06：磁场监听与页面前台状态绑定

**修改范围**：SensorPage；与 P1-01 同批实施。

1. 分离用户希望检测的状态与实际已注册状态，仅当用户已开始检测且页面处于 RESUMED 时注册。
2. 进入后台或离开该 Tab 立即注销。短暂退后台后返回同一页面，若用户未主动停止且权限仍有效，则自动恢复；切换 Tab 离开后回到磁场页默认待开始。
3. 检查 registerListener 返回值，失败时回到待开始状态，在原提示区域显示原因，允许重试。
4. 暂停、恢复但尚未收到新事件时显示待测值，避免把上次读数冒充实时读数；去除每次事件的 error 日志。

**验收**：同一时刻最多注册一次，退后台/切 Tab/销毁后注销；返回按上述策略恢复；注册失败不会显示正在检测；连续前后台切换后事件不重复。

## P2-07：订阅刷新合并与查询新鲜度控制

**修改范围**：[SubscribeHelper.kt](/C:/Android/driverSkr/CameraDetection/app/src/main/java/com/spyfinder/hiddencamera/detectorapp/utils/SubscribeHelper.kt)、BaseActivityVBind、MainActivity、SubscribePage/SubscribeViewModel。

1. 普通前台刷新统一由一个入口请求，去除基类/子类与首次加载/生命周期的重复 force 调用；商品价格加载仍独立。
2. 帮助类维护一份在途权益查询。同一时段的普通调用共享结果，不是各自排队执行完整查询；离开一个页面不取消其他调用方正在等待的共享查询。
3. 普通权限检查可复用短期缓存；购买成功、用户主动恢复购买要求更新的查询代次。若旧查询开始于购买之前，其结果不得覆盖购买后状态；必要时在旧任务之后合并安排至多一轮新查询。
4. 保留当前的未知/有效/无效语义：查询失败不当成未订阅，也不清除之前已确认的权益。继续保留购买回调代次保护。
5. 保留有限超时，查询结束、失败、取消都清理在途状态；避免一次失败导致后续永远等待同一个已失效任务。

**验收**：模拟多个同时进入的查询只调用一次底层权益刷新；弱网超时后可重试；旧查询晚到不能撤销新购买状态；主动恢复能得到满足其时间要求的新查询结果。真机商店验证需使用测试订单，单元测试不能证明真实购买链路已通过。

**订阅放行**：不修改 SubscriptionGate 的临时开关与 TODO。
