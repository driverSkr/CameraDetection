## 1. [P2] 迟到的服务公告会清除本次扫描已确认的视频协议证据

位置：`NetworkScanner.kt:76`、`152-159`。

触发过程：设备首先通过默认端口探测确认 RTSP，之后收到同一 IP 的新服务公告（例如 HTTP 8080）。`discovered()` 为安排补充分析调用 `analyzed.remove(ip)`，随后的 `refreshRow()` 立即失去旧分析中的 RTSP 证据和端口详情。如果重新探测超时、设备关闭连接，或用户此时取消扫描，最终快照中原本已确认的摄像头相关线索就会消失。新公告在分析进行中到达时，旧一轮结果也会被直接丢弃。

影响：设备从摄像头相关线索降级为信息不足，线索数量减少，结果及保存的历史不再包含这次扫描实际观察到的协议响应。

验证：在 PLY110（Android 16）上，通过反射注入已确认 RTSP 的分析结果，然后调用生产 `discovered()` 接收 HTTP 公告；断言原 RTSP 证据立即消失。再注入失败重试结果并调用生产 `refreshRow()`，确认 finding 变成 INSUFFICIENT、riskLevel 变成 0。这是受控状态复现，未在真实局域网中模拟服务时序。

建议：将本次扫描已经观察到的证据与待分析状态分开保存。新增公告可以重新排队、使完成状态失效，但不应删除既有正向证据；后续结果按协议、端口和来源增量合并。

## 2. [P2] 同一硬件的兼容服务能力被误判为身份冲突

位置：`DeviceDescription.kt:25-26`，下游 `DeviceIdentity.kt:39`。

触发过程：同一设备返回两份 UPnP 报告，厂商和型号相同，但分别声明 MediaRenderer 和 MediaServer。合并已经支持保存多种服务能力，却仍把任何不同的 `upnp_type` 当作身份冲突。

影响：单独一份报告能根据 Smart TV 型号识别为“可能是电视”；加入另一份兼容能力报告后反而显示“设备类型未确认 / 身份线索冲突”。同一硬件同时提供媒体播放和媒体服务器能力，并不构成相互矛盾的硬件身份。

验证：在真机测试中直接调用生产 `mergeReports()` 和 `classify()`，使用相同厂商、Smart TV 型号以及两种媒体服务类型，确认两个能力均保留，但 `identity_conflict=true` 且原电视分类丢失。

建议：将服务能力集合与硬件身份冲突判定分离。兼容能力只做汇总；互相矛盾的硬件身份仍保留冲突提示。
